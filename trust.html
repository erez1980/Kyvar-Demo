DEPLOYMENT & DATA RESIDENCY

Where your data lives.

By default, everything runs in your environment. The hosted option exists for teams that would rather not operate the control plane.

Self-hosted by default

The control plane, its PostgreSQL database and the runtimes all run on infrastructure you control — Docker Compose or Kubernetes, in the cloud or on-prem. Users, connectors, credentials and the audit trail never leave it.

Runtimes dial out

A runtime opens no inbound ports. It connects out to the control plane and authenticates with a token of its own — one runtime cannot read, claim or complete another's work.

The model is yours

Bring your own model provider and key. The key lives on the runtime, never in KYVAR's database. Beyond the integrations you configure — that provider, your notification channels, your SIEM — nothing leaves your environment.

CONTROLS IN THE PRODUCT

What is built in today.

Every item below is in the shipping product and covered by automated tests that run on every change.

Identity & access
  • Single sign-on with OIDC and SAML 2.0
  • SCIM 2.0 provisioning — joiners, movers and leavers from your directory
  • TOTP multi-factor authentication with single-use recovery codes
  • Roles (admin, operator, viewer) enforced on every API route
  • Per-connector access grants: who may use which account, and how far
  • Tenant isolation — another tenant's record is a 404, never a 403
Credentials & secrets
  • Encrypted at rest (Fernet) and write-only through the API — no endpoint returns a stored secret
  • Delivered per run only to the runtime executing that run, authenticated by its own token
  • KYVAR's own control-plane tokens stripped from the agent's environment
  • AWS roles supported, so no long-lived key need exist at all
Change control
  • Approval gate: risky changes park until a person decides
  • Separation of duties — the requester cannot approve their own change
  • Environment-scoped approver groups (production can require a different group)
  • Approvals expire and escalate on deadlines you set
  • Risk judged from the environment of the credentials, not a label the client sends
Audit & monitoring
  • Hash-chained, tamper-evident audit trail, verifiable on demand
  • Streamed to your SIEM as it is written — HTTP collector or syslog (RFC 5424)
  • CSV export with each event's hash
  • Per-tenant data retention policies — off by default, every purge recorded
  • Prometheus metrics and a request ID on every response
AI & data handling
  • Context KYVAR gathers for a run (tickets, logs, asset details) is redacted for credentials before it reaches the model
  • Command output never goes on the run record — the command and its outcome do
  • KYVAR does not train models on your data
  • A daily token budget caps model spend
Application & operations
  • HttpOnly, Secure session cookies with CSRF protection
  • Nonce-based Content Security Policy, HSTS and strict security headers
  • Per-route rate limits and login throttling
  • SSRF guard on the outbound URLs a customer can configure
  • Backups leave the box, and a restore is rehearsed on every deploy

Stated limit: redaction covers what KYVAR assembles and sends. What the agent reads for itself with its own shell on the runtime is bounded by the connector's permissions and the approval gate, not filtered. Prompt injection is bounded, not eliminated.

RESPONSIBLE DISCLOSURE

Found something? Tell us.

Our contact for security reports is published in /.well-known/security.txt — today that is hello@kyvar.io.

What to send

What you found, how to reproduce it, and the impact you observed. A proof of concept helps; exploitation does not.

Please don't

Access other customers' data, degrade a service others rely on, or test social engineering. Test against a deployment of your own or a pilot we set up.

What we do

A person reads every report, confirms receipt, and keeps you informed until it is fixed. Please give us reasonable time before you disclose.
